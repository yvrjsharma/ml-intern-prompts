Train an image-editing LoRA for `Qwen/Qwen-Image-2.1` that takes ONE transparent (RGBA) image of an object and a camera instruction, and returns the same object from the requested viewpoint, also as a transparent RGBA image. We have ground truth, so prove the result with numbers against the base model.

**Verified facts, do not re-derive.**
- Qwen-Image 2.1 is one model for generation and editing; it edits when given `image=`. Its VAE is natively RGBA. Inference: `QwenImage21Pipeline` from diffusers main, 40 steps, no CFG (`true_cfg_scale=1.0`), `transformers>=5.17`.
- **Trainer: use ostris/ai-toolkit** (`arch: qwen_image_2`). The maintainer added 2.1 support on 20 Sep, alpha-channel training the same day (`model.model_kwargs.rgba: true`), and reference-image resolution matching on 22 Sep (`model_kwargs.match_target_res`, default true). Editing is configured by giving the dataset a `control_path` (the source view) next to the target images; captions belong to the targets. Its UI default model path is `Comfy-Org/Qwen-Image-2.1` (pre-quantized int8); for a clean bf16 run point `name_or_path` at `Qwen/Qwen-Image-2.1` and set `quantize: false`. Use torch 2.13 or newer: issue 1054 (LoRA saved with all-zero `lora_B`) was closed as not reproducible on current torch.
- **Fallback trainer only: DiffSynth-Studio** `examples/qwen_image_21/model_training/train.py` with `--data_file_keys "image,edit_image" --extra_inputs "edit_image"`. Three open reports against it this week: pure-noise outputs with diverging loss on 2.1 (issue 1706, no fix yet), 26 s/step edit training on an H100 at 1 MP (issue 1704, user-patched in the text encoder), and a validation script that never loads the trained weights (issue 1702). Only use it if ai-toolkit fails the smoke test, and then verify each of those three things yourself.
- Whatever trainer: after 50 steps load the saved adapter and **assert that `lora_B` tensors are non-zero** and that one training pair's output visibly changed versus the base model, before spending on the full run.
- Data: `suvadityamuk/google-scanned-objects` (CC-BY 4.0), 43 shards `data/gso-train-000NN.tar`, about 26 objects per shard, 1,030 real scanned household objects, each with a normalized `.glb` and a JSON with `category` (mostly Toys, Shoes, Consumer Goods, Bottles). **The meshes are Z-up**: with a Y-up camera a shoe renders standing on its toe. **They have no consistent front direction**, which is why the pose grammar below is relative.
- Rendering measured at 0.36 s per 768 px view with trimesh + pyrender on a laptop CPU. Pin `PyOpenGL==3.1.7` (3.1.9 crashes in `glGenTextures`); on Linux jobs use `PYOPENGL_PLATFORM=osmesa` or `egl`. Blender `bpy` with Cycles CPU is the fallback.
- Prior art: `fal/Qwen-Image-Edit-2511-Multiple-Angles-LoRA` (absolute poses like `<sks> right side view elevated shot medium shot`). Do not copy its absolute grammar; see below.

**Pose grammar (relative azimuth, absolute elevation).** Because neither scanned objects nor user uploads have a known front, every instruction is relative to the source view:
`<orbit> rotate the camera {45|90|135|180} degrees to the {left|right}, {low angle|eye level|elevated}`
(180 needs no left/right; write `rotate the camera 180 degrees, eye level`). Also include 20% of pairs with `<orbit> keep the camera angle, {low angle|elevated}` so elevation-only moves are learned. That is 7 azimuth moves x 3 elevations plus 2 elevation-only moves = 23 instructions.

**Step 1. Render on CPU (`cpu-upgrade`, all 8 cores in parallel).** Hold out 40 objects across categories for testing. For every object render 24 views: 8 azimuths in 45 degree steps x 3 elevations (-20, 10, 40 degrees = low angle, eye level, elevated), 768x768 RGBA, transparent background, soft three-point lighting, no ground plane, Z-up handled correctly. Frame from the bounding sphere so the object spans 55 to 65% of the frame at eye level and the same camera distance is used for all 24 views of one object. Reject objects where any view covers under 8% of the frame. Push renders plus pose metadata as a dataset. Expect about 25,000 views and under 30 minutes wall clock.

**Step 2. Build edit pairs.** Per training object sample 4 pairs. The source is always an eye-level view at a random azimuth; the target is the source azimuth plus one of the 7 relative moves (or the same azimuth for the 20% elevation-only pairs) at one of the 3 elevations. About 3,900 pairs, roughly balanced over the 23 instructions. Lay them out for ai-toolkit: target PNGs with caption `.txt` files in one folder, the matching source PNGs under the same file names in the `control_path` folder. Before training, run 10 pairs through the base model with and without appending "The image has alpha channel and the background is transparent." and use whichever keeps transparency better.

**Step 3. Baseline first.** 2.1 has some built-in viewpoint ability. On 40 held-out objects x 4 targets (160 edits) run the untouched base model with (a) a plain instruction such as "Show the same object with the camera rotated 90 degrees to the right" and (b) our `<orbit>` grammar. These are the numbers the LoRA must beat.

**Step 4. Train.** Rank 32, alpha 32, learning rate 1e-4, resolution 768, bf16, gradient checkpointing, cache text embeddings, on one `a100-large`. Smoke test 50 steps first and report seconds per step. Then set the step count so training costs at most 8 USD (target 1,500 to 2,500 steps); if 768 px cannot reach 1,500 steps inside that, drop to 640 px rather than steps. Checkpoint every 500 steps. Log loss to Trackio.

**Step 5. Evaluate with ground truth, inside a 6 USD cap.** Measure seconds per edit in the smoke test and scale these counts to fit:
- Checkpoint selection: a fixed 48-edit subset (12 objects x 4) at 20 steps, for the base model and every checkpoint.
- Final comparison: the full 160 held-out edits at 40 steps for the base model (both baselines) and the chosen checkpoint only.
Metrics per edit, fixed seed: alpha IoU against the true mask; LPIPS and PSNR against the true render, both composited on mid-gray; DINOv2 similarity to the true render. Break results down by rotation size (45 to 180) and by elevation change, so we can see whether hidden sides, which must be invented, stay plausible. Choose the checkpoint with the best LPIPS that does not lose alpha IoU.

**Step 6. Out-of-domain check (about 1 USD).** Scanned household objects are not what people will upload. Generate 12 transparent subjects with the base model's text-to-image mode (a cartoon mascot, a sneaker, an armchair, a robot toy, a potted plant, a game character, a perfume bottle and so on), run an 8-view eye-level orbit on each with the chosen checkpoint by chaining 45 degree moves from the original image (never from a generated one), and publish contact sheets plus one animated turntable per subject. Say honestly where it breaks.
